# 资产与配置使用内嵌关系库持久化

Status: proposed（随资产管理首批实现落地转 accepted）

资产、资产属性、资产关联、变更历史与配置快照是**关系型数据**（多对多关联、字段级 diff、按关系查询），现有 Server 的 JSON 文件落盘方式无法支撑查询与一致性；同时本项目的交付约束是"内网离线 + 单二进制 Server + 交叉编译（linux amd64/arm64/arm）"。因此决定：资产域使用**内嵌关系库 SQLite**，驱动选 `modernc.org/sqlite`（纯 Go、无 CGO），数据库文件与既有本地状态文件同级。

需要澄清的是"Server 完全无状态"这一既有说法：它指的是**指标数据归时序库**；Server 本地早就有 JSON 持久化（告警处置 `alert_acks.json`、保留策略、安全事件、看板 `dashboards.yaml`、审计）。引入关系库属同层演进而非定位改变，因此**不迁移**这些既有 JSON 状态——只承接关系型数据，避免无收益的搬迁。

## Considered Options

- **继续用 JSON 文件**：关系查询、字段级 diff、并发写一致性都要自己实现，删除测试结论是复杂度会在多个调用方重现 → 拒绝。
- **外部数据库（PostgreSQL/MySQL）**：与"内网离线 + 单二进制 + 一键部署"冲突，且给客户增加运维对象 → 拒绝。
- **内嵌 SQLite（选定）**：单文件、可备份、支持事务与索引；纯 Go 驱动不破坏 CGO_ENABLED=0 的交叉编译与离线包。

## Consequences

- 新增二进制构成变化（引入纯 Go SQLite 驱动），需在 `build/cross-compile.sh` 的产物验证与离线包体积评估中复核。
- 数据库文件必须纳入既有升级备份流程（`internal/server/upgrade` 的备份替换路径），并在 `server.yaml` 暴露路径配置项。
- 迁移路径：首次启动按现有节点清单与实例注册表**导入一次**（幂等、来源标记为采集），导入失败不影响主流程。
- 若将来关系型数据规模超出单机 SQLite 能力，替换为外部数据库需要改动持久化适配层——这是本决策"较难回退"的部分，故记录在案。
