## 1. 目标与非目标

**目标（三块，按依赖顺序）**

| # | 能力 | 说明 |
|---|---|---|
| 1 | **采集** | 按配置把指定路径的日志**增量**采集上来（带节点、来源、时间戳），进程重启不丢进度 |
| 2 | **检索** | 时间范围 + 关键词/正则 + 节点/来源过滤，服务端分页；结果可定位到「哪台机的哪个文件」 |
| 3 | **日志告警联动** | 「日志里匹配到某模式」变成可告警信号，并**复用既有告警链路**（规则 / 静默 / 抑制 / 收敛 / 通知 / 处置） |

**非目标（明确不做）**

- **不引入全文索引与查询语言**：本项目零检索依赖（`go.mod` 直接依赖 16 条，无 bleve/lunr/meilisearch 之类），
  C2 不做「类 Lucene 查询语法」。检索是**有界的扫描**（时间分片 + 命中上限），代价与范围可预期。
- **不做日志聚合统计引擎**：计数、速率、TopN 交给时序库——日志匹配会同时产出指标（见 §7），不必另造一套。
- **不做实时 tail -f 推送**：按采集周期增量上传（与既有 nginx/SSH 日志读取同构）。
- **不做外部转发**（syslog / Loki / ES）：把日志推给别人是另一类需求，且会改变「数据留在本系统」的隐私假设。
- **不做日志内容脱敏的自动识别**：只提供**上传范围收窄**（默认按模式过滤，见 §8）与行长度截断。

## 3. 架构与数据流

```
被监控机                                      Server
┌───────────────────────────┐               ┌───────────────────────────────┐
│ log source(配置：路径/模式) │               │ POST /api/v1/logs（X-Agent-Secret + 体量上限）
│   ↓ 增量读（offset 落盘）  │  ──批量──▶    │   ↓ 校验/截断/限速              │
│   ↓ 按模式过滤/多行合并    │               │   落盘：<DataDir>/logs/<source>/<YYYY-MM-DD>/<node>.log
│   ↓ 计数 → 指标（告警用）  │  ──report──▶  │   ↓ 保留策略按天清理            │
└───────────────────────────┘               │ GET /api/v1/logs?from&to&q&...（扫描+上限）→ 前端
                                            └───────────────────────────────┘
```

两条通道各司其职：**日志走 `/logs`（体积大、可丢、按周期批量）**，
**日志匹配计数走既有的指标通道（小而关键、必须可靠、可告警）**。二者的失败互不牵连。

## 4. 采集侧设计

### 4.1 配置（`agent.yaml` 新增段）

```yaml
logSources:                      # 缺省为空 = 不采集任何日志（与既有「危险能力默认关闭」惯例一致）
  - id: applog                   # 唯一标识；同时作为来源名与指标前缀
    paths: ["/var/log/myapp/app.log"]   # 支持多个路径（同一来源多文件）
    # 只上传匹配这些模式的行（推荐显式给出，见 §8）；`all: true` 表示全量上传
    patterns:
      - { name: err, regex: "(?i)\\b(error|exception|fatal)\\b" }
    # 多行合并：堆栈/JVM 异常等一条日志跨多行时，按「行首模式」把续行并入上一条
    multiline:
      startPattern: "^\\d{4}-\\d\\d-\\d\\d"   # 行首不匹配则并入上一行
      maxLines: 50
    maxLinesPerRound: 2000       # 单轮单文件最多上传行数（上限保护）
    maxBytesPerRound: 4194304    # 单轮单文件最多读取字节（默认 4 MiB）
```

### 4.2 增量与状态

- 读取形状照抄 `nginx_access.go`（Seek + 逐行 + 轮转检测：文件变小即视为轮转/重建从头读）。
- **offset 必须落盘**（与该实现的关键差异）：`<数据目录>/log_offsets.json`，
  按 `source|path` 记录 `{offset, inode?, updatedAt}`；进程重启后从上次位置继续。
- 首次启动与「文件不存在」的语义要显式定死（见 §12 决策 3）：建议**首次从文件尾开始**（不回溯历史，
  避免一上线就把几十 GB 历史日志灌进 Server），并在日志里明说这一点。

### 4.3 上行与背压

- 批量上传：单请求最多 N 行 / M 字节（与 Server 侧上限对齐，见 §5）。
- 上传失败（Server 不可达）：**本轮丢弃并计数**，不落盘缓冲。
  理由：日志是「尽力而为」的数据，落盘缓冲会引入「缓冲满了怎么办」的一串新问题（且磁盘是 Agent 上最不该被占满的资源）；
  丢弃必须**可见**——产出 `log_dropped_total{source,reason}`（走指标通道），否则就是静默丢数据。
- 速率上限：单节点上行默认 ≤ 1 MiB/s（可配），超出部分丢弃并计数。

## 5. 服务端存储与上行接口

### 5.1 上行接口

```
POST /api/v1/logs          # 复用 X-Agent-Secret 鉴权；MaxBytesReader 限制请求体（默认 4 MiB）
body: { "node": "...", "group": "...", "source": "applog",
        "lines": [ { "ts": 1727..., "text": "...", "matched": "err" } ] }
```
- 校验：`source` 必须已在本机配置里声明（否则拒绝，避免被当成任意写入通道）；
  行数/行长度上限（单行截断，默认 8 KiB）；`text` 内不得含控制字符（转义处理）。
- 限速：按节点做简单令牌桶（内存态），超限回 429（Agent 侧丢弃并计数）。

### 5.2 落盘布局

```
<DataDir>/logs/<source>/<YYYY-MM-DD>/<node>.log     # 追加写，一行一条 JSON（带 ts/pattern）
```
- 按「来源 / 日期 / 节点」分片：查询时可按时间与节点**只打开少数文件**，这是「无索引也能有界扫描」的基础。
- 单文件上限（默认 256 MiB）与**每日总量上限**（默认 1 GiB/来源，超出丢弃并计数）——容量必须有天花板。
- 保留：接入 `retention`（默认 7 天，与 reports 同量级，见 §12 决策 6）。

### 5.3 检索接口

```
GET /api/v1/logs?from=<ms>&to=<ms>&q=<substr>&regex=<re>&nodes=&sources=&limit=200&cursor=<opaque>
```
- 先按时间与来源筛出文件列表（**有界**），再逐文件扫描；命中 `limit` 即停并返回 `truncated: true`
  （前端明确提示「结果被截断，请缩小时间范围」——静默截断会让人以为日志就这么多）。
- 排序：默认时间倒序（最常用）；`cursor` 为「已扫到哪个文件/偏移」的不透明游标。
- 权限：新增权限点 `logs:read`，并按节点分组做范围过滤（复用 `auth.FilterByGroup`）。
- 正则查询**限制长度与复杂度**（RE2 无回溯风险，但仍限制模式长度），避免用户写出代价高的扫描。

## 7. 日志告警联动（推荐方案：日志匹配 → 指标）

**做法**：Agent 在采集日志的同时，对每条 `patterns[].name` 计数；每个采集周期把**增量**产出为指标：

```
<id>_log_match_total{source="applog", pattern="err", node="...", group="..."}   # counter（周期增量）
<id>_log_lines_total{source="applog", node="..."}                               # 本周期上传行数
<id>_log_dropped_total{source="applog", reason="rate|size|unreachable"}         # 丢弃可见性
```

**为什么这么选**：

- 规则的输入本就是「指标名 + 阈值」，因此**前端零改动**即可配告警（选指标、设阈值、设持续时间），
  并且自动获得静默 / 抑制 / 收敛 / 通知 / 处置三态的全部既有能力；
- 指标是**跨节点可聚合**的：`sum(log_match_total{pattern="err"})` 这类判断天然成立，而事件式通道不擅长这个；
- 与 C1 的产物形态一致（都是「模板/采集器产出指标」），不引入第二套告警语义。

**保留的选项（阶段二）**：把「高危匹配」额外上报为**事件**（复用既有安全事件通道：`payload.SecurityEvents`
→ `IngestSecurityEvents` → `evalSecurityEvents`），好处是告警详情里能**直接看到原始日志行**。
代价是要新增一个事件类别并扩 `validSecurityCategory`；阶段一先用指标 + 从告警跳转到日志（§6）达到同样效果。

## 8. 安全与隐私

日志与指标不同：**内容不可控**（可能含密码、个人信息、业务数据）。因此：

- **默认只上传匹配模式的行**（`patterns` 必填；要全量必须显式 `all: true`）。
  这条默认值是 C2 最重要的隐私决定：把「上传范围」从「整个文件」收窄到「你明确关心的行」。
- 单行截断（默认 8 KiB）+ 控制字符转义 + 请求体上限：避免单行异常把存储与界面拖垮。
- 通道鉴权复用 `X-Agent-Secret`；`source` 必须是本机已声明的（不接受任意来源名）。
- 界面读取受 `logs:read` + 节点分组范围约束；**是否记录「谁查过日志」到审计**见 §12 决策 8。
- 明确写在文档里的一句话：**日志内容会离开被监控机**。运维在配置 `logSources` 时应当知道这一点。

---

## 9. 容量与保留

- 三层天花板：单轮读（Agent）→ 每日每来源总量（Server）→ 保留天数（retention）。任一层超限都要**计数可见**。
- 容量估算写在文档里（例如：单节点 2000 行/轮 × 1 分钟 × 每行 200 B ≈ 0.6 GB/天/节点），
  让运维在开启前能算清楚——不然「开了日志把盘写满」是迟早的事。

## 12. 待你拍板（8 项）

| # | 决策点 | 我的建议 | 理由 |
|---|---|---|---|
| 1 | 存储与检索形态 | **按来源/日期/节点分片的文本文件 + 有界扫描**，不引入索引/检索引擎 | 零新依赖；容量与查询代价都可预期。若将来需要全文检索，再评估引入（那时数据已在盘上，加索引不必重采） |
| 2 | 默认上传范围 | **只上传匹配模式的行**（`patterns` 必填；全量需显式 `all: true`） | 隐私与体积两项都受益；「先想清楚要什么，再上传」 |
| 3 | 首次启动的起点 | **从文件尾开始**（不回溯历史），并在日志中明确提示 | 避免上线瞬间把历史日志灌爆 Server；需要历史请用其它工具导入 |
| 4 | 上行失败的处理 | **本轮丢弃 + 计数可见**（`log_dropped_total`），不做磁盘缓冲 | 日志是尽力而为的数据；磁盘缓冲会引入一串新问题（上限、清理、对齐），而 Agent 上磁盘最不该被日志占满 |
| 5 | 日志告警的接入方式 | **日志匹配 → 指标 → 既有阈值规则**；事件式（能看原始行）留阶段二 | 前端零改动、自动获得静默/抑制/收敛/通知/处置；跨节点可聚合 |
| 6 | 默认保留期 | **7 天**（与 reports 同量级），可按来源覆盖 | 与既有保留策略的默认量级一致，避免「一个新开关悄悄吃掉磁盘」 |
| 7 | 上行限速默认值 | **1 MiB/s/节点**，超出丢弃并计数 | 给 Server 与网络一个确定的保护上限 |
| 8 | 查询日志是否入审计 | **暂不入审计**（审计面向「写操作」），但在接口上留 `logs:read` 权限点 | 审计目前是「管理操作」语义；把查询也塞进去会淹没真正关键的操作记录。若要留痕，建议单独做「访问日志」而非混进审计 |

## 附录：与 C1 的关系

- C1 的 `file` kind 是**快照**（每轮读文件末尾取当前值），C2 是**增量采集**（按行、按周期、可回溯分页）；
  两者是不同语义，刻意没有合并：把「当前值」和「日志流」混在一个配置里，用户会分不清自己拿到的是哪种。
- C1 的「本机护栏」经验直接沿用：C2 的 `logSources` 同样是「默认关闭 + 显式声明路径」，
  且**只读**（不写、不删日志文件）。
