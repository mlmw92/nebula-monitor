# 日志检索能力：后端选型可见化（设计件，批次 23）

> 收 P1 里最后一处真缺口「字段检索 / 全文索引」。调研（只读）之后，这条缺口的性质与原始描述不同：
> **不是"必须自己造索引"，而是"部署选型 + 能力看不见"**。本批把这件事说清楚、让它在界面上看得见，
> 并把"本地后端不建索引"从"欠账"改记成**产品决定**。

## 1. 为什么做

原始缺口写的是"未做：全文倒排索引、百万行级字段筛选的性能保证"。调研发现的**事实**是：

| 后端 | 检索怎么做的 | 全文/字段索引 |
|---|---|---|
| **local** | 目录按「时间 × 来源 × 节点」分片 → 反向逐行读，关键词 `strings.Contains`、字段逐行等值；三层预算兜底（64 MiB / 20 万行 / 页 ≤1000） | **没有**。这是刻意的：文档反复写过"另建索引会引入索引与分片不一致""**半套索引比没有索引更危险**""需独立立项" |
| **victorialogs** | 关键词、正则、字段、节点、Pod **全部下推**成 LogsQL，由 VL 自带的倒排索引检索；平台只解析/排序/分页 | **已具备**（`victorialogs.go:532-538`） |

也就是说：**要百万行级索引检索，路径是"用 VL 后端"，不是"平台自建索引"**。而平台**已经支持**
这个后端（`logBackend: local|victorialogs`），配置即得。

那还缺什么？缺**让人知道自己在哪一种能力下**。现在：

- 配置里选了哪个后端，界面上**看不到**；
- 本地后端的"单次最多扫 64 MiB / 20 万行"这条硬边界，**只在被截断时才显形**（而且要用户先撞上）；
- 于是"我要查一个月前的日志、要按字段筛百万行"这个真实需求，用户不知道**当前部署做不到**，
  也不知道**换个配置就能做到**——这正是"能力不可见"的代价。
- 反过来，切到 VL 之后扫描诊断恒为 0，运维会怀疑"是不是没生效"（换存储 ≠ 迁移历史数据，
  旧文件不会自动进 VL），而**没有任何地方**说明这一点。

## 2. 目标形态

### 2.1 只读能力端点：`GET /api/v1/logs/backend`（`logs:read`）

与 `/api/v1/system/retention` 同一取向（**只读、如实报告、不猜**）：

```
{
  "backend": "local",
  "capabilities": {
    "fullTextIndex": false,          // 该后端是否具备全文索引
    "fieldIndex": false,
    "scanBudget": {"bytes": 67108864, "lines": 200000},   // 仅 local 有；VL 为 null
    "notes": ["本地后端不做倒排索引：索引与分片的一致性风险由搜索后端承担，要百万行级检索请切到 VictoriaLogs"]
  },
  "storage": {                        // 该后端实际存了什么（探测所得，失败就如实说失败）
    "sources": 12, "nodes": 3,
    "oldestMs": 1790000000000, "newestMs": 1791336000000,
    "bytes": 48234496
  }
}
```

- **local**：`storage` 由现有的目录遍历算出（来源数、节点数、最早/最晚、总字节）；
- **victorialogs**：`storage` 改为探测 VL 的可达性与条数上限（**探测失败要如实报告"探测失败：
  连接被拒"而不是 0**——0 会被读成"没有日志"）；
- 两种后端都不做任何写入。

### 2.2 界面上把它说出来

日志页顶部一行（**只在需要时醒目**）：

- 本地后端：「当前后端：本地（有界扫描，单次最多 64 MiB / 20 万行）· 百万行级字段筛选需切到 VictoriaLogs」；
- 被截断时（已有提示）末尾加一句同样的指引——**用户撞到边界的那一刻才是最需要这句话的时候**；
- VL 后端：「当前后端：VictoriaLogs（索引检索）· 只检索切换之后的日志；历史本地文件不会自动迁入」。

### 2.3 文档：把"不建索引"记成决定，而不是欠账

- 能力全景该行：`部分实现` → `已实现（后端能力边界明确）`，把"自建倒排索引"写成**明确不做**
  并附理由（半套索引更危险；索引一致性由搜索后端承担）；
- README 的选型段落补一句：**日志量大 / 要按字段筛百万行 → 用 VL 后端**，并说明"换存储 ≠ 迁移历史"。

## 3. 需要拍板的决策点

| # | 决策 | 建议（理由） |
|---|---|---|
| **D1** | 自建倒排索引做不做 | **不做**（沿用文档既有判断）。半套索引与分片不一致的风险高于收益；要做百万行级，用 VL 这种成熟搜索后端 |
| **D2** | 能力端点是否探测真实状态 | **探测**（来源数/时间跨度/字节；VL 的可达性）。只回配置值等于把"配置"当"能力"——与 `/system/retention` 那次"如实报告原因"同一取向 |
| **D3** | 探测代价 | 复用现成的目录遍历（检索本来就要列文件）；**给上限**（列到一定条目数就停并标记），不做全量统计 |
| **D4** | 界面提示的强弱 | **默认一行静默小字**，被截断时升级为提示条。常驻大横幅会变成噪声（大多数部署一天跑不到边界） |
| **D5** | 要不要顺手统一"后端能力"的表达 | **要**：`capabilities` 用固定字段（`fullTextIndex`/`fieldIndex`/`scanBudget`），后续加后端（如有）不用改前端协议 |

## 4. 与既有能力的边界

- **不改检索行为**：本批只加只读端点与提示，`Query` 的路径、预算、截断语义一行不动。
- **不改存储**：不动落盘格式、不动 VL 写入字段（那些是上一批的事）。
- **权限沿用 `logs:read`**：它只暴露"能力与规模"，不暴露日志内容。
- **不引入"自动切后端"**：切换是部署决策（涉及历史数据的可见性），平台只提示、不代劳。

## 5. 迁移与回滚

无 schema 变更、无数据写入；回滚旧版本时新端点 404、前端提示消失，不影响检索。

## 6. 验证计划

1. **单测**：能力端点在两种后端下的 `capabilities` 形状（local 有 `scanBudget`、VL 为 null）；
   `storage` 的边界（空目录 → 来源 0 且**不报错**；VL 不可达 → 明确报"探测失败"而不是 0）；
   探测上限（文件数很多时提前停止并标记）。
2. **实机**：dev-server 现在是 `local`（VL 已装但停用）→ 端点应报 local + 预算 + 真实来源/时间跨度；
   再**临时切到 VL**（改配置重启）确认：`fullTextIndex=true`、`scanBudget=null`、提示文案切换、
   并且**关键词与字段检索仍然工作**（这是"接线已经通了"的实证）。切回。
3. **回归**：日志检索的现有用例全绿（本批不该碰到它们）。

## 7. 实施记录（2026-10-07，1.30.43）

D1~D5 按建议落地：不自建索引、能力由**后端实现自己回答**（放进 `LogStore` 接口，而不是接口层
按配置推断——后者是"把配置当能力"）、探测给上限、提示默认静默、能力字段固定。

### 7.1 落地内容

| 层 | 改动 |
|---|---|
| 接口契约 | `LogStore` 新增 `Capability()`；类型 `Capability` / `ScanBudget` / `StorageStats` 定义在 `backend.go`（与其它契约同处） |
| 本地后端 | `capability.go`：`probeStorage` 走「来源/日期」两级目录，**只 stat 与列举、不读内容**；文件数触顶（2 万）即停并标 `Truncated`；非日期目录名不参与时间跨度 |
| 外部后端 | 探测 = 一个**带 7 天时间窗的只读查询**（字段目录），不扫全量；失败如实回报；容量/保留期平台不掌握，故留零值并在 Notes 说明 |
| 接口 | `GET /api/v1/logs/backend`（`logs:read`）；未启用集中日志 → 503（与检索同一取向） |
| 前端 | 日志页头部一行静默小字（后端 + 预算 + 来源数与时间跨度）；**被截断时**把指引升级为"要在大范围里按字段筛百万行，需切到 VictoriaLogs"；探测失败单独一条警告，明说"这不代表没有日志" |

### 7.2 实施中定的几处

1. **探测失败与"没有日志"必须分开**：`StorageStats.Err` 非空即探测失败，界面单列一条警告
   （"这不代表没有日志——是平台问不到后端"）。把前者显示成 0 会被读成"日志丢了"。
2. **探测失败不影响能力判断**：外部后端不可达时仍声称 `fullTextIndex=true`——能力是后端的属性，
   与"这一刻可达吗"是两件事（用例钉住）。
3. **载荷不完整就不说话**：前端在 `backend` 字段缺失时整行不显示，而不是默认按"本地"渲染
   （对着不认识的载荷替它宣称后端种类，是凭空造事实）。
4. **挂载时不阻塞首屏**：能力提示与检索并行拉取（它只影响一行字）。
5. **上传上限沿用 probeMaxEntries=20000**：宁可不全（报"至少这么多"），也不为一个提示把目录扫一遍。

### 7.3 用例与结果

- `logstore/capability_test.go`（4 组）：本地空目录 = 0 条且**不报错**（正常状态）、分片统计
  （来源/节点/时间跨度/字节，非日期目录名不计）、列举触顶标截断、外部后端可达时访问了后端
  且**无写入**、不可达时带出探测失败且不否认能力。
- `api/logs_backend_test.go`（1 组，覆盖 4 种情形）：未启用 503、本地载荷（无索引 + 有预算 +
  真实存储数）、外部载荷（有索引 + `scanBudget` 为 **null** 而不是 0 + `probeError`）、无权限 403。
- `LogsView.test.js` 新增 3 组：本地（说清有界扫描 + 预算 + 来源数，截断时指向切后端）、
  VictoriaLogs（说索引检索、不再提切后端）、探测失败（"这不代表没有日志"）。
- `go build`/`go vet`/`go test ./...` 30 包全绿；前端 **19 文件 114 项**通过（新增 3 项）、`vite build` 通过。

### 7.4 实机验证结果（2026-10-07，dev-server 升 Server 1.30.43；Agent 未动）

跑法：`dist/logcap-e2e.py local`（默认后端）与 `python3 logcap-e2e.py vl`（临时切到 VL 后）。
切换与还原由 `dist/logcap-switch-vl.sh switch|restore` 做（先备份 `server.yaml`、**还原走备份文件**
而不是反向改回去）；VL 原本是 `disabled + inactive`，由 `dist/vl-start.sh` 起、验完停回。

**① local 模式：15 项全过。**`backend=local`、`fullTextIndex/fieldIndex=false`、
`scanBudget={67108864, 200000}`、`notes` 2 条；**存储探测是真的**：`sources=3`、`nodes=1`、
`2026-10-06 ~ 2026-10-07`、`bytes=3495450`（≈3.3 MiB）、`truncated=false`、无 `probeError`；
**两条独立路径对账**：存储探测的来源数与 `/logs/fields` 的来源数**都是 3**；检索仍返回数据
（扫描诊断 `scannedBytes=366 / scannedLines=1 / files=1`，是真实数值）。

**② 切到 VL（本批最关键的一条）：14 项全过。**

| 判据 | 实测 |
|---|---|
| 能力如实切换 | `backend=victorialogs`、`fullTextIndex=true`、`fieldIndex=true`、**`scanBudget=null`**（不是 0）、`notes` 3 条 |
| 可达性探测 | `probeError` 缺席（探测成功）；`storage.sources=1`——它**是真去问 VL 的**（`stream_field_values` 取 `source`），不是拿配置充数 |
| **索引检索仍然工作** | 显式 7 天窗口取到 5 行（`node=VM-0-10-ubuntu`、`source=nginx_access`）；由首行挑出的关键词 `WuEL` 再查仍命中（关键词确实下推给 VL） |
| 扫描诊断 | 恒为 0（外部后端没有"逐文件扫描"这回事） |
| **写入也跟着切** | 造一条唯一标记的 404 访问 → **19 秒后**在 VL 上按标记可检索（`node=...`），即「请求 → access.log → Agent → Server → VL → 检索」整条链路通 |
| **换后端 = 换存储** | 直接问 VL：切换前 6 小时的行**一条都不在** VL 里（它们在本地分片）；VL 侧来源数从本地的 3 变成 1 |

**③ 顺带纠正的两条口径（都不是产品缺陷，是我核对脚本的前提错了）**：

1. **默认时间窗是最近 1 小时**（`logs_api.go:307`，刻意为之）。VL 里存的是更早的数据时，
   不带 `from/to` 去查就是查不到——那是"我的查询"的问题，不是"检索坏了"。VL 模式的核对因此
   **必须显式给窗口**（第一版在这里误报过一次）。
2. **Agent 的隐私默认值：只上传命中 `patterns` 的行**（`config.go:193/203`，启动期强制校验，
   `config.go:515`）。本机 `nginx_access` 配的是 `err4xx`/`err5xx`，所以打一个 `/` 拿 200 的
   测试请求**本来就不会被上传**——第一版拿它验"写入是否切过去"，把正常行为误判成了丢数据。
   **造流量要造会被上传的行**（这里是 404），否则验的是空气。

**④ 一处已知的表述余量**：外部后端的载荷里 `bytes`/`nodes` 仍是 0（`logStorageView` 这两个字段
没有 `omitempty`），Notes 已说明"容量与保留期平台不掌握"。前端只读 `sources` 与时间跨度，
不显示这两项，所以界面无误导；若将来给第三方消费这个端点，应改成"省略"而不是"给 0"。

**收尾**：`server.yaml` 已从备份还原（确认无残留键）、服务重启后 local 模式复验 **15 项全过**、
VL 停回 `inactive`。切换期间写进 VL 的那几行只存在于 VL（换后端是换存储，这是设计行为，测试机上无需处理）。

### 7.5 仍未覆盖边界（不得视为通过）

- 浏览器实点（那一行提示与截断提示的实际观感）；
- 真实 VL 的**大范围**字段筛选性能（本批只验"能力声明与可达性"，没有压测）；
- 本地后端在**接近预算上限**时的现场手感（该机日志量远小于 64 MiB）；
- **探测失败的现场形态**（`VL 地址不通 → probeError → 界面"这不代表没有日志"`）本轮没走：
  切过去时 VL 是可达的。用例已覆盖该载荷（`logs_backend_test.go`），但实机未验。
