# 资产关系视图（全库总览 + 筛选下钻）（设计件，批次 22）

> 收能力全景「资产关系与拓扑」这条 P0 的最后一块欠账：**全库视图**（现在只有"以某个资产为中心"
> 的 N 跳邻域）。能力全景自己写了难点所在——"那需要先解决**布局与聚合**（全库规模下力导向图不可读）"。
> 本设计件就是回答这句话：**用聚合回答"库里整体有什么关系"，用筛选+上限回答"某个子集长什么样"**，
> 而不是把整张图倒进力导向里。

## 1. 为什么做

现有的关系入口只有一个：资产详情抽屉里的「关系图」= 以该资产为中心、最多 3 跳 / 500 节点的邻域
（`GET /api/v1/assets/{id}/topology`）。它能回答"这台机器牵动谁"，回答不了三类同样常见的问法：

1. **"库里现在整体有哪些关系？"**——有多少 `runs_on`、多少人工维护的边、哪些类型之间有边。
2. **"某类关系都长什么样？"**——例如"所有 `depends_on` 依赖"、"所有人工认领过的关系"。
3. **"纳管了但没有任何关系的资产有多少？"**——这是台账质量的信号（有资产、没接线）。

而这三问的答案**不需要**把整张图画出来：1 是聚合、3 是计数、2 是"筛选后的子图"。

## 2. 现状事实（改造面）

| 项 | 现状 | 位置 |
|---|---|---|
| 单资产邻域 | 已有：depth ≤ 3、节点 ≤ 500、**显式 truncated** | `asset/service.go:534-569`、`store.go:1586`（`topologyAround`） |
| 关系读取 | 只有 `linksOf(assetID)`（某资产的出入边）与 `topologyAround`；**没有任何聚合查询** | `store.go:1674`、`store.go:1586` |
| 前端图组件 | `TopologyGraph.vue`：ECharts 力导向，按类型着色、失联画红圈、人工边虚线、点节点换中心 | `web/src/components/asset/TopologyGraph.vue` |
| 范围裁剪 | 邻域在 **SQL 之后按节点集合过滤**（`service.go:566-569`），中心资产范围外返回 `ErrOutOfScope` | 同上 |
| 路由与菜单 | 路由是 layout 下的扁平子路由；菜单在 `Sidebar.vue`；命令面板按路由前缀分组（`CommandPalette.vue:118-126`） | — |
| 既有上限常量 | `DefaultTopologyDepth/Nodes`、`MaxTopologyDepth/Nodes` | `asset/model.go`（关系图邻域边界一节） |

**两个必须沿用的既有口径**（不是本批发明的）：

- **范围裁剪在 SQL 里下推**（列表/统计已经这么做）；邻域因为要逐跳展开才只能事后过滤。
  本批的两个接口都能下推，**必须下推**——否则受限用户能从"总览计数"里看出范围外的规模。
- **截断必须显式回报**（`truncated`），不能让界面把"一部分"显示成"全部"。

## 3. 目标形态：一页两段

新页面「关系视图」`/assets/topology`（菜单归「资产与配置」组，与「资产台账」同级），
页内上下两段：**上=总览（聚合），下=图（筛选后的子图）**。点总览的某一行 → 自动带上该筛选刷新下面的图。

### 3.1 总览：按 `(来源类型 × 关系种类 × 目标类型 × 边来源)` 聚合

新接口 `GET /api/v1/assets/link-stats`（`assets:read`），返回：

```
{
  "groups": [
    {"fromType":"middleware-instance","kind":"runs_on","toType":"host","source":"discovery","count":42,
     "sample":{"fromKey":"redis:10.0.0.10:7000","toKey":"VM-0-10-ubuntu","fromName":"…","toName":"…"}},
    {"fromType":"middleware-instance","kind":"depends_on","toType":"middleware-instance","source":"discovery","count":3, …}
  ],
  "assetsWithoutLinks": 12,     // 纳管了但没有任何关系的资产数（台账质量信号）
  "totalLinks": 45
}
```

- 一行的量级是"类型对 × 种类 × 来源"（几十行），**规模无关**，也不会被截断。
- 两个范围维度（节点分组 + 业务标签）在 SQL 里下推，`assetsWithoutLinks` 同样按范围算。
- `sample` 给一条真实边的两端（含名字），让"这行到底是什么"不用点进去就能看懂。

### 3.2 图：按筛选取子图（复用现有力导向组件）

新接口 `GET /api/v1/assets/topology?kind=&type=&source=&node=&limit=`（`assets:read`）：

- 先按筛选选出**边**，再把边的两端取成**节点**——与"以某资产为中心"不同，这里是"以一组边为中心"。
- 硬上限：节点 ≤ `MaxTopologyNodes`（500，沿用）、边 ≤ 新增 `MaxTopologyEdges`（建议 1000）；
  被截断时 `truncated=true`（沿用既有约定，界面必须说明"只显示了一部分"）。
- 筛选维度：`kind`（关系种类）、`source`（人工/采集）、`type`（资产类型）、`node`（归属节点）。
  多选取并集、彼此取交集，与列表页的筛选语义一致。
- 布局仍用力导向：**不做别的布局**（层级/弧线是另一个大件），"全库不可读"由上一段的聚合解决。
- 范围裁剪同样在 SQL 里下推。

### 3.3 与总览的联动

点总览的某一行 → 图带 `kind + fromType + source` 三个参数刷新；图上方显示当前筛选（可清除），
与其它页"生效中的条件必须看得见"的取向一致。

## 4. 需要拍板的决策点

| # | 决策 | 建议（理由） |
|---|---|---|
| **D1** | 两段同批做，还是先做总览 | **同批做**。只给数字（"有 42 条 runs_on"）不能点进去看形态，等于把问题推给下一批；而图这一段是复用现有组件，成本主要是新查询 |
| **D2** | 图的默认筛选与上限 | **默认不筛 kind**（全给）+ 节点 500 / 边 1000 + 显式截断。默认就藏东西会让人以为"关系只有这些"；上限与截断是既有约定，界面必须说清 |
| **D3** | 独立页还是并进资产台账页 | **独立页**（`/assets/topology`）。资产台账页已经有列表 + 筛选 + 抽屉，再把总览与图塞进去会让它变成三个东西 |
| **D4** | 要不要"只看人工维护的边"开关 | **要**。`source=manual` 是"人认领过哪些关系"的直接答案，成本只是一个筛选参数 |
| **D5** | 无边资产怎么处理 | **图里不显示**（这张图关注关系，不是资产清单）；但总览给一个 `assetsWithoutLinks` 计数——"纳管了却没接线"是有价值的信号 |
| **D6** | 要不要为全库换布局（层级 / 弧线 / 聚类） | **不做**。全库规模的可读性问题由**聚合层**解决，不由布局解决；换布局是另一个大件，且要先把"关系语义"定得更细（现在只有 4 种） |

## 5. 与既有能力的边界

- **单资产邻域接口不变**（`/assets/{id}/topology`）：它回答的是另一个问题，两个入口并存。
- **不新增关系种类、不改关系写入路径**：这是纯读能力。
- **同权限点**：两个新接口都用 `assets:read`（它们暴露的都是资产信息，与列表/详情一致）。
- **不引入图数据库/外部图引擎**：数据就在 `asset_links`，聚合与子图各一条 SQL。

## 6. 迁移与回滚

- **无 schema 变更、无数据写入**：纯读接口 + 新页面。回滚旧版本时新页面 404（菜单项也随之不存在），
  不影响任何既有功能；台账库不需要处理。

## 7. 验证计划（本批必须做，不能只跑单测）

1. **单测（store/service）**：
   - 聚合按 `(fromType, kind, toType, source)` 分组正确，计数与 `linksOf` 逐条相符；
   - **范围裁剪**：受限身份（节点分组 + 业务标签）的聚合计数只含范围内的边，`assetsWithoutLinks` 同口径；
   - 子图筛选：`kind` / `source` / `type` / `node` 各自生效、叠加取交集；
   - 上限与截断：边数超限时 `truncated=true` 且节点数不超上限；
   - 空库 / 无边资产的边界（`groups` 为空数组而非 null）。
2. **实机（dev-server，数据现成）**：该机有 42 条实例 + 3 条主从 + 容器边——
   预期总览出现 `middleware-instance→host runs_on 42`、`middleware-instance→middleware-instance depends_on 3`、以及容器侧的若干行；
   图的节点/边数与总览对得上。再**用一个受限身份**核对：计数只含它范围内的边。
3. **回归**：`go test ./...` 全绿；前端组件用例（总览渲染、点行带参刷新图、截断提示、权限门控）。

### 8.1 落地内容

| 层 | 改动 |

### 8.2 与设计件不一致的地方（实施中定的）

1. **"两端都要可见"从隐含要求变成硬要求并写进用例**：设计件只在 §3.2 提了"范围裁剪在 SQL 里下推"，
   落地时明确为**一条边只有两端都在可见范围内才计入/才出现**——只判一端时，受限用户能从计数或
   图上多出来的那个节点看出范围外资产的存在与规模。聚合与子图两侧都有负例用例。
2. **类型/归属节点维度按"两端任一命中"**：设计件没写清是"两端都必须是"还是"任一端"。选前者会把
   绝大部分边筛掉（图上只剩两条腿一样的结构），且"某类资产参与的边"才是运维想问的。
3. **关系图组件加了"数据模式"**（`TopologyGraph.vue`）：原来只支持"自己按 assetId 取数 + 点节点换中心"。
   新增 `data` 与 `reCenter` 两个 prop：数据模式不取数、不显示跳数（那里所有节点都是 0 跳，
   显示"（中心）"是一句假话）、点节点改为向外抛 `node-click`（页面拿它打开资产详情）。
   **截断提示按模式给不同措辞**：邻域模式的边界是节点数（能缩跳数），数据模式常常是边数（只能缩筛选）
   ——说错是哪一种，用户不知道该往哪调。
4. **无边资产的计数口径**：排除短命运行时对象（容器/工作负载）与被忽略的资产，与台账首页的资产数可比；
   否则这个数字会包含几百个滚动更新留下的 Pod，"没有接线"的信号会被淹掉。
5. **样本边显示名字、精确自然键放 `title`**：台账列表已是这个取向（名称 + 副标题），且同名实例不少
   （该机有 6 个 redis），要核对时得有准值。

### 8.5 未覆盖边界（不得视为通过）

- **浏览器实点未做**：只有组件用例与"产物里有这些串"的核对，没有真实点击（点总览行 → 图刷新、
  点节点 → 跳详情、几百节点下的力导向可读性）。
- **上限在真实规模下的手感未验**：该机只有 46 条边 / 44 节点，离 1000 边 / 500 节点还很远，
  这两个值是按"与邻域上限同量级"推的。
- **多集群 / 多节点规模**（例如几百台机器 × 每台几十个实例）下的总览行数与筛选体验未验。
