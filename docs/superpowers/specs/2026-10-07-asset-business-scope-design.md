# 资产的资源范围扩展（资产分组 / 业务范围）设计件

> 状态：**待拍板**（决策点 D1~D5 见 §5）。落地前的现状取证见 §2，全部结论可跳转核对。
> 上游：全景表 §3.13 `资产的资源范围扩展` 行（**P0 / M**，判定"未实现"，要求"**不得退化为前端隐藏**"）。

## 1. 问题

现在的授权范围**只有一个维度：节点分组**（`auth.Scope{Mode, Groups}`）。业务上常见的问题是另一类：
"给支付业务线的运维一个账号，只能看到支付相关的资产"，而支付线横跨多台机器、多个资产类型——
按节点分组划不出来（一台机器上可能同时跑支付与风控），也没有任何"资产集合"的概念可用。

全景表把这条判定为 P0，原因不是"少一个筛选框"，而是**授权的表达能力**：现在的范围模型逼着运维
在"给全量"与"按机器切"之间二选一，前者过宽、后者过细且与业务无关。

## 3. 目标与不变量（落地时必须守住）

1. **服务端强制**：不得只做前端隐藏/过滤（全景表对该行的明确要求）。前端回显是体验，判定在服务端。
2. **fail-closed**：范围配置异常（列了不存在的值、解析失败）时**不给权限**，绝不放大为全部。
   沿用 `ExpandPrincipal` 的既有取向（`auth/policy.go:60-67`：restricted 且分组为空 = 无资源权限）。
3. **handler 不自行判定**：新维度必须进 `internal/server/auth`，由统一工具计算，handler 只消费结果。
4. **不引入隐式授权**：范围只能由"人明确配置 + 人明确打的标签"决定；**不从采集值自动推标签**做范围
   （自动来源一变，授权范围就跟着变，这种漂移在授权上是不可接受的）。
5. **一致性**：自定义角色的业务范围**不得超过创建者**（与 `CreateRole` 现有的分组约束同一取向）。

## 4. 方案对比

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 标签选择器**（推荐首批） | 范围增加一个维度：`业务范围 = {标签键: 值}` 列表（如 `env=prod`、`biz=pay`）；服务端把它折算成"可见资产集合"，与节点分组维度一起参与判定 | 无新实体、无新 CRUD；`asset_labels` 与按 label 过滤的 store 能力**已在**；打标签已有批量入口；与"运维能理解的东西"一致 | 依赖标签**真被打上**——没打标签的资产在受限用户眼里就是不存在（fail-closed 的必然代价，必须在界面与文档里说清） |
| **B. 显式资产组实体** | 新建 `asset_groups`（集合）+ 成员表 + CRUD + 设范围时选组 | 语义最直白（"这一组资产"），不依赖打标签 | 新表 + 新页面 + 成员维护（还得决定成员能否批量导入、采集资产进组后消失怎么办）；**首批成本明显高于 A**，且 A 的标签本质上就是"动态分组" |
| **C. 只做筛选不做授权** | 台账加"按业务标签筛选"，范围仍只有节点分组 | 成本最低 | **不解问题**：授权表达能力没变，全景表这条仍是未实现 |

**建议：先做 A**。A 与 B 并不冲突——A 落地后如果确实需要"人工固定的集合"，可以在同一套范围内加上
"显式集合"作为第三种选择器类型，而不必推翻 A（选择器是可扩展的：标签选择器 / 未来集合选择器）。

## 5. 决策点（请拍板）

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| **D1** | 业务范围的承载物 | A 标签选择器 / B 显式资产组实体 / C 只筛选 | **A**（可扩展，成本最低；B 的"动态分组"其实由标签免费得到） |
| **D2** | 两个维度（节点分组 / 业务范围）如何组合 | ① **取交集**（两者都要放行）② 取并集（任一放行即可）③ 互斥（配了业务范围就不看分组） | **① 取交集**。授权维度应是"且"：过宽会让人以为"配了业务范围就收窄了"却仍能看别的机器；③ 会让存量角色的语义凭空变化（更危险） |
| **D3** | **未配置**该维度时的语义（三态里的第三态） | ① 未配置 = **该维度不生效**（等价于不限，仅另一个维度起作用）② 未配置 = 无权限（什么都不给） | **①**。② 会让所有存量角色在升级后瞬间失权（全局角色除外也会炸）；但**"配置了但解析为空/全是不存在的值"必须 fail-closed 到"无权限"**，与 §3.2 一致——两者的区别要在实现里显式写出并有用例 |
| **D4** | 首批覆盖哪些接口 | ① 仅资产台账读（列表/详情/导出）② + 写（编辑/批量/忽略删除）③ 再 + 巡检 ④ 再 + 日志/容器/操作 | **①→②**。资产域先闭环（读+写都按新维度收窄，否则"看得见但改不了/改得动看不见的都怪"）；业务维度对**日志/容器/操作**的语义不同（那三者的范围是按**节点**收窄的，"日志属于支付线"必须先有资产标签到日志来源的映射），另开一批 |
| **D5** | 选择器认哪些标签键 + 越范围的响应 | ① 只认**一个约定键**（如 `biz`，键名可配）② 任意标签键都能进范围 ③ 越范围沿用资产侧现状 **404**（`assetInScope`）还是改成 403（`permission-matrix` §6 对单节点的规定） | **①**（任意键会让"给某台机器打个标签"意外变成授权开关）+ **沿用 404**（与资产现状一致；§6 的 403 是针对节点路径参数的规定，两者差异需在矩阵里写明，不要偷偷不一致） |

## 7. 明确不做（首批）

- **不从采集值/资产属性自动推标签**做范围（§3 不变量 4：自动来源一变，授权范围就跟着漂）。
- **不做全库"业务视图"**（那是报表域的事）。
- **不改 `handleGroups` / 节点分组语义**（两个维度并存，不是替换）。
- **不覆盖日志/容器/操作的范围**（见 D4：语义不同，另开一批）。
- **不顺手补 §8.8 那两处聚合缺口**（与本设计无关；它们是真缺口，但应单独一批处理，避免混淆验收）。

## 8. 验收判据（可核性）

1. 受限用户（业务范围 `biz=pay`）:`GET /api/v1/assets` 只返回带该标签的资产；`GET /api/v1/assets/{id}` 对
   范围外资产返回 404；`PUT /api/v1/assets/{id}`、`POST /assets/batch`、`GET /assets/export` 同样收窄。
2. **负例优先**：范围列了不存在的标签值时，可见集合为空（而不是"不限"）；范围解析失败 → 无权限（不 500）。
3. 未配置业务范围的存量角色行为**逐字不变**（回归用例：升级前后同一账号的可见资产集合一致）。
4. 自定义角色无法给自己超出创建者的业务范围（400 且提示）。
5. 前端在"因为范围而空"时给出可读原因（不是干瘪的 0 条）。

## 9. 拍板后的落地顺序（供确认）

`auth 模型与合并规则（含三态）` → `可见集合计算 + store 下推` → `资产读写接口接线 + 负例` →
`前端配置与空态` → `文档对账` → `dev-server 实机验证（该机已有主机/中间件/Pod 三类资产，可造受限账号实测）`。
