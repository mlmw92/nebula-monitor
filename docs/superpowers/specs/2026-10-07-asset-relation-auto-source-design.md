# 资产关系的自动来源（设计件，批次 21）

> 收能力全景「资产关系与拓扑（依赖 / 归属 / 影响传播）」这条 P0 的最后一块：
> **`depends_on` / `exposes` 目前只有人工来源**，于是告警影响面能看到的边只有"实例跑在哪台机器上"
> 与"Pod 属于哪个工作负载"——而真正想回答的问题（"这台库挂了，谁跟着受影响"）恰恰没有数据。

## 1. 为什么做

影响面的口径是**关系邻域**（`README.md:373` 明确写了"不从指标推断依赖"）。这不是缺陷，是刻意的
边界：指标相关性推出来的"依赖"会把影响面变成一张不可靠的图。但它的代价是——**邻域里有什么，
完全取决于边有多少**。现在边只有三类（见 §2.1），且都不表达"谁依赖谁"，于是：

- 主库挂掉时，从库不在邻域里（反过来也一样）；
- 用户只能看到"这台机器上跑了什么"，看不到"这台库倒下会牵连谁"。

同时，**关键数据其实已经在手里**：`ReplicaOf` 一路从采集器报到了 Server，却在上报映射那一步被丢掉
（见 §2.2）。本批做的是"把已经采到的信息用起来 + 修掉一处会造错边的判定"，**不新增推断**。

## 2. 现状事实（改造面）

### 2.1 已有的自动边（全部在 server/receiver，Agent 侧不建边）

| 边 | 建立位置 | 数据来源 | 条件 |
|---|---|---|---|
| 中间件实例 → 主机（runs_on） | `receiver/assets.go:81-86` | 上报节点 `p.Node` | 每轮实例清单 |
| Pod → 主机（runs_on） | `receiver/assets.go:196-199` | `K8sPod.Node`（spec.nodeName） | 该主机资产已存在 |
| Pod → 工作负载（member_of） | `receiver/assets.go:208-211` | `OwnerKind/OwnerName`（ReplicaSet 一跳已在采集侧解析） | 本轮清单里含该工作负载 |

`LinkDiscovered` 的契约（`asset/service.go:418-436`）：**两端资产都必须已存在**，否则报错且不建边；
被人工抑制过的边跳过，人工认领过的边不降级回 discovery。**不造占位资产**是既有取向
（`assets.go:100-101`：宁可没有边，也不编一个我们并不认识的主机）。

### 2.2 已经采到、却在映射时被丢弃的字段

`instanceObservations`（`receiver/assets.go:254-315`）只取 Instance / Name / Group / Role / Topology /
Version / Up / Status / Image —— **`ReplicaOf` 没有进 `assetObs`**（结构体见 `assets.go:228-244`），
而它一直存在于上报载荷里：

| 类型 | 字段 | 采集侧怎么填的 | 可信度 |
|---|---|---|---|
| redis | `ReplicaOf` = 主库 `host:port` | INFO 的 `master_host:master_port`，经 `normalizeRemoteAddr`（`collector/redis.go:103-120`）；cluster 副本在 `redis.go:273` 填 | 高 |
| mysql | 同上 | `SHOW SLAVE STATUS` 的 `Master_Host/Port`，经 `normalizeInstanceAddr`（`collector/mysql.go:107-116`）；**组复制（GR）下显式清空**（`mysql.go:133/137`，避免把 GR 成员误判成主从） | 高 |
| postgres | 字段存在但**没有任何采集器填它**（`model/metric.go:223`） | 待补：standby 上从 `pg_stat_wal_receiver.conninfo` 解析主库地址（`collector/postgres.go:243-258` 现在只查了 `pg_is_in_recovery()` 与延迟） | — |

另有一处**不能直接用**的表示：中间件查询接口把哨兵发现的 master 写成 `sentinel:<名字>`
（`query.go:1580-1581`）——那不是地址，**不能当自然键**（用它建边会去查一个不存在的资产）。

### 2.3 现存 `runs_on` 有一处偏差（本批建议一并修）

`assets.go:81-86` 一律把实例挂到**上报节点**，完全不看 `Instance` 地址的主机部分。后果分两种：

- `Instance = 127.0.0.1:6379`（本机实例）→ 挂在采集它的机器上，**正确**；
- `Instance = 10.0.0.9:6379`（exporter 模式、或跨机采集）→ **照样挂在采集机上**，而那台机器不是它的宿主。

这不是"少一条边"，而是**多一条错边**：影响面会漏掉真正跑该库的机器、并把采集机误标成宿主。
按既有取向（关系宁少而准、不猜拓扑），这是要修的。

### 2.4 消费方对"边"的假设（新增边无需改协议）

- `Service.Links`（`service.go:603-610`）与 `Topology`（`service.go:520-569`）遍历时**方向无关**地看两侧
  （`store.go:1582`），任意 kind 一视同仁；BFS 对每条边两个方向都走；
- 载荷组装按"对端是否等于 To"给出 `direction`（`api/asset_api.go:643-646`）；
- 告警影响面（`api/alert_impact_api.go:54-123`）复用同一套邻域；
- 前端 `TopologyGraph.vue` 画 `from→to` 箭头（`:135`）、人工边虚线（`:107`）、标签显示 kind，
  `AssetListView.vue` 的 `KIND_LABELS` 给中文名。

→ 新增一条 `depends_on` 边，这四处**都能直接显示**，只需补一个中文名与图例说明。

## 3. 目标形态

### 3.1 主从依赖边（`depends_on`）：副本 → 主库

| 项 | 口径 |
|---|---|
| 方向 | `副本 --depends_on--> 主库`（副本依赖主库）。问"主库挂了谁受影响"就是从这条边往上游走 |
| 来源 | `ReplicaOf`（redis / mysql 已采；postgres 待补采集，见 §4 D4） |
| 自然键 | `TypeMiddlewareInst` 的自然键是 `<type>:<addr>`（`assets.go:72`），而 `ReplicaOf` 与 `Instance` 走**同一套地址归一化** → 主库资产在台账里时能精确命中 |
| 两端必须存在 | 主库不在台账（外部库、未纳管）→ **不建边、不造占位**，只记一条 debug 日志 |
| 顺序 | 实例循环里副本可能先于主库出现 → **先落全部实例、再统一建边**（与"先工作负载后 Pod"同类：这是正确性，不是优化） |
| 属性 | `ReplicaOf` 同时进实例属性（`replicaOf`）——让"这条边为什么存在"在台账里查得到，而不是只存在于关系图里 |
| 幂等 / 人工优先 / 抑制 | 全部沿用 `LinkDiscovered`，不引入第二套写边路径 |

### 3.2 纠正 `runs_on` 的宿主判定

| 项 | 口径 |
|---|---|
| 判定 | 取 `Instance` 的 host 部分，与**上报节点的地址**比对：等于 `p.IP`、或为回环地址（`127.0.0.1` / `::1` / `localhost`）→ 视为本机，建边；否则**不建边** |
| 判定不了 | host 是主机名而节点地址是 IP（或反之）、多网卡多地址 → **不猜**：不建边，但把观测到的 `addrHost` 留在实例属性里（"我们知道它指向别处，但不知道是谁"） |
| 存量错边 | 只删**自动建的、且地址主机与当前上报节点不符**的边（`source=discovery`）；**人工认领过的（`source=manual`）一律不动** |
| 为什么是删除而不是抑制 | 抑制的语义是"人工禁止它再出现"；这里是"我们建错了"。若将来这台机器真的成了宿主（迁移后重报），边应该能重新长出来 |

## 4. 需要拍板的决策点

| # | 决策 | 建议（理由） |
|---|---|---|
| **D1** | 主从依赖边做不做 | **做**。数据已采、映射处丢弃、方向明确；这是"依赖"这一类里**唯一有直接证据**的来源，收益大且不引入推断 |
| **D2** | 主库不在台账时怎么办 | **不建边、不造占位**（与 pod→host 同一取向）。造占位会凭空多出一堆"外部资产"，而它们没有采集、没有责任人、还会污染清单与告警匹配 |
| **D3** | 要不要一并修 `runs_on` 的宿主判定（§2.3） | **修，并清理存量错边**（仅 discovery 来源）。留着它等于在影响面里埋"采集机=宿主"的假事实；不清理的话，旧错边会永久保留（边只增不减） |
| **D4** | postgres 的 `ReplicaOf` 补不补采集 | **本批补**（store 字段已在、只差一处查询）——否则三种主从库里只有两种能用。改动很小：standby 上解析 `pg_stat_wal_receiver.conninfo`；取不到就留空（**不猜**） |
| **D5** | 中间件实例的**集群归属**（member_of → 集群资产） | **本批不做**。`Group` 是 Agent 本地配置别名（`redis.go:119` 取 `cfg.Name`），跨 Agent 可能同名不同集群；而且"集群"当前没有对应的资产类型——要做先定集群资产模型，属于另一批 |
| **D6** | 端口暴露（`exposes`） | **本批不做**。`ListenerStat`（`model/metric.go:58-69`）有 Port/Process/PID，但 `0.0.0.0` 的归属、PID 与实例的对应都不稳定；错一条 `exposes` 会直接影响"这台机器暴露了什么"的判断，宁缺勿错 |
| **D7** | K8s `service → pod` | **本批不做，且要先补采集**：清单里**没有 Service/Endpoint**，Pod/Workload 投影还丢掉了 labels（`model/metric.go:592-615`）。属 Agent 侧改动，另立一批 |

## 5. 与既有能力的边界

- **人工优先不变**：人工建的边不会被采集降级（`store.go:1269-1281`）；人工删掉的边进入抑制表，采集不再重建。
- **不引入推断**：本批所有边都来自"对方自己报出来的地址或属主"，没有一条来自"看起来像"（端口相同、名字相似、时间相关）。
- **不新增 kind**：复用 `depends_on` / `runs_on`，`model.go:56-60` 的白名单不动。
- **Agent 侧只动 postgres 采集**（D4），其余全在 Server 侧的映射与建边；Agent 与 Server 的版本兼容性：新 Server + 旧 Agent 时 `ReplicaOf` 为空 → 只是没有新边，不会报错。

## 6. 迁移与回滚

- **无 schema 变更**：只写数据（边），`schemaVersion` 不动，旧版本 Server 打开同一个库没问题。
- **回滚**：装回旧版本 → 新边仍在（旧版本照旧显示关系，只是不会新建）；被 D3 删掉的错边**不会自动恢复**（边是数据，不是派生视图）——需要的话按备份恢复 `assets.db`。这一条要写进发布说明。
- **存量错边的清理是**幂等的**：判定基于当前上报，下一轮重新算，不会反复删建。

## 7. 验证计划（本批必须做，不能只跑单测）

1. **单测（receiver 层，构造 payload）**：
   - 副本先于主库出现仍能建边（顺序用例，与 Pod/Workload 那条同型）；
   - 主库不在台账 → 不建边、不报错、不造占位；
   - `ReplicaOf` 为 `sentinel:xxx`（哨兵发现）→ **不建边**（不是地址）；
   - GR 的 mysql（`ReplicaOf` 为空）→ 不建边；
   - `runs_on` 判定：`127.0.0.1` 建边、`p.IP` 建边、别的 IP 不建边并写 `addrHost`；
   - 存量错边的清理：只删 discovery 边，manual 边原样保留。
2. **实机（dev-server）**：起一对临时 Redis（主 + 从，从库 `replicaof` 指向主库），把它们加进
   Agent 配置 → 确认关系图里出现 `副本 --depends_on--> 主库`、方向正确、人工边未被影响；
   再核对 `runs_on` 的判定（临时把地址写成别的 IP，确认不再挂到采集机）。收尾删掉临时实例与配置。
3. **回归**：`go test ./...` 全绿；前端关系图对 `depends_on` 的中文名与图例已可读（`KIND_LABELS`）。
